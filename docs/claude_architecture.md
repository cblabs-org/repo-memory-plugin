| **Date** | 2026-09-30 |
| **Reviews** | [`SPEC.md`](../SPEC.md) v0.3, which was designed Antigravity-first |

| **Evidence** | Claude Code documentation (`code.claude.com/docs`, fetched 2026-09-30), Claude Code 2.1.284 as installed on this machine, and the esp32-app-foundation repo and its Claude Code history. Sources are listed at the end. |

## 1. Summary

**Verdict: feasible, and worth doing.** SPEC v0.3 is already harness-neutral at its core. The pipeline, claim store, views, job table, tick, MCP pull tools and data directory all carry over unchanged. What differs is a thin adapter layer:

- where transcripts live and how they're parsed;
- how hook events map onto the delivery triggers;
- which headless command runs housekeeping;
- where reports appear;
- what schedules the tick;
- how the plugin is packaged.

The two harnesses are complementary rather than equivalent:

| | Antigravity | Claude Code |
|---|---|---|
| **Event path (hooks)** | Adequate but indirect. Hooks mostly re-read the transcript; there's one hook before every model call; `PreToolUse` can only allow/deny/ask. | **Richer.** Hooks receive tool inputs, outputs and errors directly. Context can be injected at prompt submit, before and after tools, after a tool batch, and at subagent start. Async and "rewake" hooks exist. |
| **Time path (scheduling)** | **Native.** A plugin sidecar with `builtin: schedule` provides the tick. | **Missing for commands.** Desktop scheduled tasks start full model sessions (fine for reports, not for a one-minute mechanical tick). Cloud routines have no local file access. |
| **Headless housekeeping** | `agy -p`, measured at ~17k tokens of fixed overhead and ~13 s per call | `claude -p` with `--safe-mode` and minimal flags, on the subscription. Not yet measured (§4.4). |
| **Transcripts** | Pruned by the harness (only 41 of 188 esp32 sessions survive); format undocumented | 30-day default retention; the format is documented as internal and may change between releases |
| **Native memory overlap** | Antigravity's `knowledge/` store is empty (unused) | **Auto memory is active.** 13 files for esp32-app-foundation, written by the working agent and loaded every session. |

**The main reason to support both** is that esp32-app-foundation is worked on in both harnesses (188 top-level Antigravity sessions and 35 Claude Code sessions since May). A dead-end found in one should be delivered in the other. A shared claim store gives that for free.

**Recommendation:**

1. Build one core with a defined adapter interface (§6).
2. Preserve Claude Code history from P0 with a sweep-only copy of its transcripts (SPEC §18.6, rule 11). Both harnesses lose transcripts, so this can't wait for Release 2. The Claude Code adapter itself is Release 2 (R2.1–R2.3).
3. Build delivery on Antigravity first (Release 1), because it's the primary harness by volume. Keep Claude Code's richer hooks as the design check: the capability flags in SPEC §18.3 are how the delivery policy stays harness-neutral.
4. On Claude Code, make the harness's own async hooks trigger the existing tick, keeping the "enqueue, then tick" model you preferred (§4.3).

## 3. Mapping the design onto Claude Code

### 3.1 Capture

| Need | Claude Code mechanism | Notes |
|---|---|---|
| Know a session turn ended | `Stop` hook (`session_id`, `transcript_path`, `last_assistant_message`); `SubagentStop` for subagents | Equivalent to Antigravity `Stop`. Spool the entry and copy the transcript, as in SPEC §6.2. |
| Session fully ended | `SessionEnd` hook | Only a **1.5 s shared budget** by default. Too tight for anything but writing a spool file; don't copy large transcripts here. |
| Transcript location | `~/.claude/projects/<project>/<session-id>.jsonl`; subagents in `<session-id>/subagents/*.jsonl` (17 such files for esp32 on this machine) | The sweep must include the subagent files. PA workers spawned with the `Agent` tool live there. |
| Retention | `cleanupPeriodDays`, default **30 days** | Same urgency as Antigravity. On this machine the oldest esp32 transcript is from 19 August, so the sweep hasn't strictly removed everything past 30 days. Capture still shouldn't rely on it. |
| Format | JSONL. The docs say *"the entry format is internal to Claude Code and changes between versions"* | The Claude parser must be version-aware and tolerant (§5.1). |
| Commit linkage | Same as the spec (git log/reflog by time and branch) | Hook inputs include `tool_input`, so a `PostToolUse` matcher on `Bash` can record commit commands precisely. |

### 3.2 Delivery

| Trigger (spec §7) | Antigravity (spec v0.3) | Claude Code | Difference |
|---|---|---|---|
| Always-on map | Include in `GEMINI.md`/`AGENTS.md` | `@.memory/views/MAP.md` import in `CLAUDE.md` (imports recurse up to four hops) | esp32's `CLAUDE.md` already imports `AGENTS.md`. The **include syntax differs**, so each harness's map line goes in its own override file (`GEMINI.md` and `CLAUDE.md`), not the shared `AGENTS.md`. |
| Task brief | `PreInvocation` at `invocationNum == 0`, reading the first user message from the transcript | `UserPromptSubmit` receives `prompt` directly and returns `additionalContext` (30 s default timeout) | Claude is simpler and fires for every prompt, so a change of task direction can refresh the brief |
| File touch | `PreInvocation` reads the transcript tail for touched paths | `PostToolUse` with `tool_name`/`tool_input` (e.g. `Read`, `Edit`, `Write`) → `additionalContext` | No transcript parsing on the hot path |
| Error | `PreInvocation` scans the transcript tail for error text | `PostToolUseFailure` (`error`) and `PostToolUse` (`tool_response`, e.g. a failed build's output) → `additionalContext` | Direct and immediate |
| Risky action | `PreToolUse` "gate-once": deny with a reason, allow on re-issue | `PreToolUse` can return `additionalContext` **without blocking**, or `deny`/`ask` with `permissionDecisionReason`; `if` conditions such as `Bash(pio run *)` narrow the matcher | Soft delivery doesn't need the gate-once round-trip. Keep `deny` for hard gates. |
| Déjà-vu tier 1 (lexical) | `PreToolUse` on arguments; `PreInvocation` on the latest reasoning | `PreToolUse` on `tool_input`; `PostToolBatch` (after a batch of tool calls, before the next model call) reads the reasoning from the transcript tail | `PostToolBatch` is the nearest equivalent of `PreInvocation` |
| Déjà-vu tier 2 (semantic) | Spool, next tick, next `PreInvocation` (≤ ~75 s) | An **`asyncRewake`** command hook runs the check in the background and, on exit code 2, wakes Claude with the alert as a system reminder. Alternatives: a plugin **monitor** streams alerts, or a `prompt`-type hook runs the check in-line. | Claude Code can push asynchronously without waiting for a tick (§4.3) |
| Subagent briefing | Unknown whether subagents fire hooks (E8); the fallback is WORKORDER embedding | `SubagentStart` returns `additionalContext` to the new subagent; hooks inside subagents carry `agent_id`/`agent_type` | PA workers get their brief automatically, and are covered by touch, error and déjà-vu delivery |
| Pull tools | Plugin MCP server | Plugin `.mcp.json`, same server | Claude Code can defer MCP tool schemas until searched (this session shows it), which lowers the standing context cost |

### 3.3 Time path, executors and visibility

| Need | Claude Code option | Assessment |
|---|---|---|
| Periodic mechanical tick | No native command scheduler. Options: **async hooks** trigger `repo-memory tick` in the background (§4.3); an **OS scheduler** entry; or the **Antigravity sidecar** if both are installed on the machine. | Async hooks are harness-level and keep the tick as the single executor. Ticks only happen while Claude sessions are active, which is when new work appears anyway. |
| Desktop local scheduled task | Starts a full Claude session on a schedule (minimum 1 minute), only while the desktop app is open and the machine is awake. Visible under **Scheduled**. | **Wrong for the tick** (a model session per tick). **Right for reports** (§3.4). |
| Cloud routines | Run in the cloud on a fresh clone (minimum 1 hour); no access to local transcripts or the private data directory | Not usable for capture or processing |
| `/loop` | Session-scoped polling | Not suitable |
| Housekeeping runs | `claude -p` (non-bare, so it uses the subscription login) with `--safe-mode`, `--tools ""`, `--system-prompt-file`, `--json-schema`, `--output-format json`, `--no-session-persistence`, `--model haiku`, `--max-turns`, `--permission-prompts none` | See §4.4. `--bare` would be leaner but **requires `ANTHROPIC_API_KEY`**, which your quota-only constraint rules out. |
| Report conversations | Desktop local scheduled task (weekly, visible), or a background session (`claude --bg`, shown in agent view) | Matches the visibility policy (§3.4) |

### 3.4 The visibility policy on Claude Code

| Class | Antigravity | Claude Code |
|---|---|---|
| **Repo work** (visible) | IDE sessions, PA workers, bug-fixer loop | Desktop/CLI sessions and their subagents; all appear in the session list |
| **Reports** (visible) | `agentapi` conversation titled `[repo-memory] …` | A **Desktop local scheduled task**, e.g. "repo-memory weekly review", appears under **Scheduled** with a notification. The session reads the prepared review (`views/`, `QUESTIONS.md`, pending claims) and you answer there; the sweep captures your replies as evidence. |
| **Housekeeping** (hidden) | `agy -p` in a dedicated directory and project; recorded in the CLI store only | `claude -p --no-session-persistence`: **no transcript is written at all**, and `-p` sessions are excluded from the session picker and from `claude --continue` anyway |

Claude Code's hidden path is cleaner than Antigravity's. With `--no-session-persistence` there is nothing to exclude from capture. With `--safe-mode`, no plugins or hooks load inside the run, so recursion is impossible and the `REPO_MEMORY_HOUSEKEEPING` environment guard is belt-and-braces rather than essential.

Desktop scheduled tasks have two caveats:
- **Permissions.** A run in Manual permission mode stalls on the first unapproved tool. Set the report task's permission mode and "always allow" the memory MCP tools on the first run.
- **Missed runs.** Only one catch-up run happens after sleep.

## 4. The differences that matter, in depth

### 4.1 Claude Code's event path is the better one

Three properties make the Claude adapter simpler and more precise than the Antigravity one:

1. **Hook inputs carry the payload.** `PostToolUse` receives `tool_input` and `tool_response`; `PostToolUseFailure` receives `error`; `UserPromptSubmit` receives `prompt`. Antigravity's `PostToolUse` gets only `stepIdx` and `error`, and its `PreInvocation` must re-read the transcript on every model call. On Claude Code the hot path rarely touches the transcript at all.
2. **Context injection is available at the right moments.** `additionalContext` is honoured on `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `SubagentStart` and `SessionStart`. Antigravity has a single injection point: `ephemeralMessage` at `PreInvocation`, whose persistence is still unknown (E1).
3. **Subagents are first-class.** Hooks fire inside subagents with `agent_id`, and `SubagentStart` can brief them. This closes the gap the spec flags as E8 for Antigravity. Every PA worker on Claude Code gets the task brief and in-session delivery without the PA embedding anything.

**Latency is managed differently.** Claude Code has no hook before every model call; `PostToolUse` fires per tool call instead, at a comparable frequency. The spec's hook-latency budget (§7.8) still applies. Default hook timeouts are generous (600 s; 30 s for `UserPromptSubmit`), but hooks still block, so the fast-path targets stand.

### 4.2 The time path is Claude Code's gap

Claude Code can run **commands** only in response to events. Its schedulers (Desktop scheduled tasks, cloud routines, `/loop`) all run **model sessions**. There is no equivalent of Antigravity's `builtin: schedule` sidecar. Three workable answers, in order of preference:

1. **Antigravity's tick serves both** on machines where both harnesses are installed, as on this machine. Claude Code only needs capture and delivery hooks, because the tick processes the shared queue.
2. **Async hooks as tick triggers** (§4.3) on Claude Code-only machines. Processing happens while Claude sessions are active. Calendar jobs (daily publish, weekly review) run at the first tick after they fall due.
3. **An OS scheduler entry** (`repo-memory schedule install`: launchd, cron or Task Scheduler), added only if calendar jobs must run when no session is open.

### 4.3 Claude Code has harness-level async, so the tick model survives

Claude Code documents two background hook modes for command hooks:

| Field | Behaviour |
|---|---|
| `async: true` | Runs in the background without blocking. Output is discarded, and the hook's timeout isn't enforced. |
| `asyncRewake: true` | Runs in the background. On **exit code 2**, Claude is woken and the hook's stderr is shown to it as a system reminder. |

This is the harness-supervised async we looked for in Antigravity and didn't find. It fits your preference for "enqueue, then tick" without inventing a second executor:

- **The tick stays the only thing that does work.** An async hook runs `repo-memory tick`, the same entry point the Antigravity sidecar runs. It's just another trigger. `tick.lock` makes redundant triggers no-ops.
- **Suggested triggers:**
  - `Stop` with `async: true`: process the finished turn's spool promptly;
  - `SessionStart` with `async: true`: catch up on anything missed while no session was running.
- **Déjà-vu tier 2 uses `asyncRewake`.**
  1. A `PostToolBatch` hook spools a check request and starts an `asyncRewake` hook that runs the tick's interactive step for that one request.
  2. If the tick finds a match, the hook exits 2 with the alert text.
  3. Claude is woken with the alert as a system reminder. That takes seconds, where Antigravity has to wait up to a minute for the next tick.
- **Plugin monitors** are an alternative push channel: a background process per interactive session whose output reaches Claude as notifications. They're marked experimental and don't run in `-p` sessions or on Bedrock, Google Cloud or Foundry, so they're a second choice after `asyncRewake`.

**Open question C3:** does an async hook's process survive the end of the session or the app quitting? If not, work still completes on the next trigger, because jobs are durable (spec §4.3).

### 4.4 Headless housekeeping on the Claude subscription

The candidate invocation for a pure-function pipeline stage:

```
claude -p --safe-mode \
  --system-prompt-file <stage>.system.md --tools "" \
  --json-schema "$(cat <stage>.schema.json)" --output-format json \
  --model haiku --max-turns 1 \
  --no-session-persistence --permission-prompts none \
  < payload
```

The flags do the following:

| Flag | Effect |
|---|---|
| `--safe-mode` | Skips `CLAUDE.md`, skills, plugins, hooks, MCP servers and auto memory while keeping **normal authentication**, so it works on the subscription. `--bare` also skips all of that but needs an API key. |
| `--system-prompt-file`, `--tools ""` | Replace the coding-agent prompt and remove tools. This is the main lever on fixed overhead. |
| `--json-schema` + `--output-format json` | Validated output in `structured_output`, plus `usage` and `total_cost_usd` for the metrics store (spec §10.4) |
| `--no-session-persistence` | Nothing is written to disk |
| Piped stdin | Capped at 10 MB, far above the per-call payload targets |

Status and prerequisites:
- **Not measured.** On this machine, the CLI bundled with the desktop app (`~/Library/Application Support/Claude/claude-code/2.1.284/…/claude`) reports *Not logged in*: the desktop app's sign-in doesn't carry over to the standalone CLI. Measuring needs you to run `claude auth login` (or `claude setup-token` for a long-lived token for scheduled use). That's experiment C1.
- **Expected overhead.** Because the default system prompt and tools can be replaced outright, which `agy -p` doesn't allow, fixed overhead should be well below the ~17k measured for `agy -p`. C1 will confirm or refute that.
- **Whose quota.** You've asked for the Antigravity quota. On machines with both harnesses, housekeeping therefore uses `agy -p`, and `claude -p` is the executor only on Claude Code-only machines. It's one setting (`housekeeping.executor: agy | claude`), and every call's usage is recorded, so the choice can be revisited with data.

### 4.5 Transcript stability is Claude Code's biggest engineering risk

Anthropic documents the transcript JSONL as internal and version-dependent, and recommends `/export`, `claude -p --resume … --output-format json`, hooks or the Agent SDK instead. None of those give a complete, structured history of an *interactive* session after the fact, so parsing the JSONL remains the practical route. Mitigations:

- **Tolerant parser.** Keep a narrow dependency on the stable essentials (role, text, thinking, tool use/result, timestamps, `isSidechain`/subagent linkage), with unknown entry types ignored rather than fatal.
- **Version detection.** Record the Claude Code version per episode, and keep a fixture corpus of real transcripts per version. A canary test runs on each Claude Code update and flags any drop in parsed-step counts.
- **Belt and braces from hooks.** The hot path already sees tool inputs, outputs and errors. The `Stop` hook can append those essentials to a harness-neutral side-log, so a parser break loses less.
- **Retention.** Capture within the 30-day window. Optionally raise `cleanupPeriodDays` for repositories using the plugin, as a user choice.

### 4.6 Coexisting with Claude Code's auto memory

Auto memory is on by default. For esp32-app-foundation it holds 13 files, and its `MEMORY.md` index is loaded into every Claude Code session (first 200 lines or 25 KB). It overlaps directly with repo memory:

| | Claude Code auto memory | Repo memory (this plugin) |
|---|---|---|
| Written by | The working agent, in-session (costs main-session tokens) | The pipeline, from transcripts (the working agent writes nothing) |
| Scope | Per user and machine; not shared, not in git | Per repository; shared via git after review |
| Content today (esp32) | Personal workflow preferences (worker spawn mode) **and** repo knowledge ("portal assets: native stub shadowing", "CrowPanel PWR_EN bring-up", "BLE RFC #225 lead suspect") | Repo knowledge with evidence, anchors and status |
| Validation | None; the `modified` timestamp only | Anchors, re-checks on change, trust ladder |
| Reaches subagents | No (main conversation only) | Yes, via `SubagentStart` |

Recommended coexistence:
1. **Import auto memory as evidence.** Treat each auto-memory file as an import episode (`provenance: claude-auto-memory`). `feedback` entries are human-stated. `project` and `reference` entries become `observed` candidates, verified like any other claim. Several esp32 entries (native stub shadowing, CrowPanel bring-up) are exactly the gotchas the claim store should hold and share.
2. **Steer, don't disable.** Add a line to `CLAUDE.md`: repository knowledge is captured automatically by repo-memory, so auto memory should keep to personal preferences. Leave `autoMemoryEnabled` as your choice.
3. **Never write into auto memory** from the plugin. It's the user's private store.

Item 1 is refined in §4.7 (Claude-specific note 2).

### 4.7 Lessons from auto memory

Auto memory is the opposite design to repo memory. The working agent writes notes during the session, nothing processes them afterwards, and nothing re-checks them. A review of how it works, and of what it holds for esp32-app-foundation, found techniques worth reusing. The harness-neutral ones were adopted in SPEC v0.5. This section keeps the Claude-specific detail for the P2 adapter.

#### How it works

| Aspect | Behaviour |
|---|---|
| Storage | `~/.claude/projects/<project>/memory/`, one directory per git repository (shared across worktrees). `autoMemoryDirectory` moves it; `autoMemoryEnabled: false` or `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` turns it off. Excluded from the transcript retention sweep. |
| Unit | One fact per file. Frontmatter: `name`, `description`, `metadata.type` (`user`, `feedback`, `project`, `reference`). Claude Code stamps `modified` (ISO 8601) on each write to a file that has frontmatter (v2.1.214+). The esp32 files also carry `originSessionId`. |
| Loading | A `MEMORY.md` index, one line per memory. Its first 200 lines or 25 KB load at session start. Topic files are opened on demand with ordinary file tools, and each file's `description` exists to support that choice. Not loaded into subagents, except forks. |
| Budget enforcement | After each write to `MEMORY.md` the harness measures the file. Near a limit, it reminds the model to shorten it. Over a limit, the write succeeds but returns an error telling the model to rewrite the index. |
| Writing rules (from the agent's instructions) | Skip what the code, git history or `CLAUDE.md` already say. Update an existing file rather than duplicating it; delete memories that prove wrong. Convert relative dates to absolute ones. `feedback` and `project` entries carry **Why:** and **How to apply:** lines. `[[name]]` links join related memories; a link to a memory not yet written marks a gap. Save approaches the user confirms, not only corrections. |
| Reading rules | Recalled memories are framed as what was true when written. A named file, function or flag must be checked before it is recommended. |
| Consolidation | The `consolidate-memory` skill, run on request: merge overlaps, separate durable from dated entries, fix time references, drop what is easy to re-find, and keep the index under 200 lines with entries under ~150 characters. |
| Recall | The UI reports "Recalled N memories". None of the 35 esp32 transcripts contains a memory-recall attachment, so on this machine retrieval has been the agent reading the index and opening files itself. |

#### What esp32-app-foundation's auto memory shows (2026-09-30)

- **Content.** There are 12 topic files plus the index: 8 `project`, 3 `feedback`, 1 `reference`. Half carry both Why and How to apply, and those are the most useful. The gotchas are exactly what the claim store wants, such as native stub shadowing and the CrowPanel PWR_EN bring-up.
- **Status goes stale.** `ble-manager-rfc-225.md` (modified 2026-09-23 06:55Z) says WO-6 is BLOCKED and the BT-memory-release root cause is unconfirmed on hardware. Its index line says the same, so every session loads it.
  - Later on 2026-09-23, `fc974687` ("prevent Arduino BT memory release") fixed that cause, and `eaf236a7` recorded that the WO-6 hardware acceptance tests passed.
  - A week later the memory is unchanged.
- **Index drift.** The longest index line is 379 characters (hardware-config design status), against the ~150 target.
- **Gaps.** One forward link is dangling: `[[bug-fixer-lacks-pa-context]]`.
- **Volume.** 12 memories between June and September on the most active repository. Writing memory during the session only happens when the agent notices something.

#### Adopted in SPEC v0.5 (harness-neutral)

| Auto-memory technique | SPEC change |
|---|---|
| A `description` written for selection; a one-line index; topic files opened on demand | `relevant_when` line; claim index view; the agent walks MAP → index → claim (§5.3, §5.5, §7.2, §7.9) |
| **Why:** and **How to apply:** lines | `apply` line, rendered in pushes (§5.3, §7.1, §7.3) |
| `modified` stamp; "true when written"; check names before recommending them | A currency stamp on every push; the hook checks that anchored files exist (§7.1) |
| Consolidation separates dated from durable entries (and the stale BLE memory above) | `closes_when` on `open-issue`, a `resolved` status, closure evaluated by the tick (§5.3.1, §5.3.2, §8) |
| The agent's own "worth remembering" judgement | Memory-artefact writes as a triage keep rule, a salience window and `note` steps (§5.1, §6.4, §6.5) |
| Index budget measured by the harness, with a rewrite instruction | Over-budget views are re-synthesised rather than truncated (§6.8) |
| Forward links as gap markers | `gaps` from extraction feed coverage (§6.5, §9.1) |
| Saving confirmed approaches, not only corrections | Approval signals in triage (§6.4) |

#### Claude-specific notes for Release 2 (R2.1–R2.2)

1. **Auto memory is a memory artefact.** Add `~/.claude/projects/<project>/memory/` to the Claude adapter's `triage.memory_artefacts`. Writes to it appear in the transcript as `Write`/`Edit` tool calls with their full text, so compaction turns them into `note` steps without any hook. A real-time `PostToolUse` hook isn't needed.
2. **Import auto memory with exposure awareness.** This refines §4.6 item 1 and SPEC §12.2.2, which treat `feedback` entries as human-stated.
   - **The risk.** An auto memory is the agent's paraphrase, so under P13 it is a lead, not evidence. Once delivery pushes claims in Claude Code (R2.2), the agent can restate a pushed claim in auto memory, and importing that memory would support the claim with itself.
   - **The rule.**
     - Resolve `originSessionId` to the source session's episode, and take evidence from that episode's human-authored steps and tool outcomes.
     - If the source transcript is gone, import the memory at most as `observed`, never `confirmed`.
     - Check the source episode's exposure steps. A memory written after exposure to a claim that it restates is marked `echo_of`, not support.
3. **Report stale auto memories; don't fix them.** The plugin never writes into auto memory (§4.6). The weekly report can list auto-memory entries that claims or commits contradict (the BLE entry above would qualify) as proposed work for the human. SPEC §9.4 already proposes fixes this way for documents that contradict verified claims.
4. **Subagent memory is a second store, and it lives in the repo.** A subagent definition's `memory` field gives it its own auto memory:
   - `user` → `~/.claude/agent-memory/<agent>/`;
   - `project` → `.claude/agent-memory/<agent>/`, committed to git (the docs recommend this scope);
   - `local` → `.claude/agent-memory-local/<agent>/`.

   Its `MEMORY.md` (200 lines / 25 KB) loads when the subagent starts, and Read, Write and Edit are enabled automatically. If PA workers adopt it:
   - treat it as another memory artefact and import source, under the rules in note 2;
   - don't generate into it, because the subagent edits it too;
   - expect it to overlap with the `SubagentStart` brief, and steer it towards agent-specific working notes in the agent definition, as §4.6 does for auto memory.

   In esp32-app-foundation, `.claude` links to `.agents`, so project-scope files would land in `.agents/agent-memory/`.
5. **Don't copy:**
   - writing memory during the session as the main path (it costs main-session tokens and depends on the agent noticing);
   - the lack of re-checking;
   - a flat 200-line index (fine for dozens of notes, not for thousands of claims);
   - loading into the main agent only.

## 5. Engineering notes for the dual-harness core

### 5.1 Normalised episode input

The spec's episode format (§5.1) is already harness-neutral. The Claude Code parser maps:

| Claude Code JSONL | Episode step |
|---|---|
| `user` message with text | `user` |
| `assistant` text block | `agent` |
| `assistant` thinking block | `reasoning` |
| `tool_use` + `tool_result` (Bash) | `command` with outcome and error excerpt |
| `tool_use` Edit/Write | `edit` (path only) |
| `tool_use` Read | `read` (path only) |
| Subagent transcript (`subagents/*.jsonl`) | `subagent` → nested episode |

Measured composition for the 35 esp32 Claude Code sessions (spec Appendix A.2): 70% tool traffic, so the spec's compaction target (≥ 3×) applies equally.

### 5.2 Normalised hook events

Both adapters translate native hook payloads into one internal event model, so delivery logic is written once:

| Normalised event | Antigravity source | Claude Code source |
|---|---|---|
| `session.turn_end` | `Stop` | `Stop` / `SubagentStop` |
| `prompt.submitted` | `PreInvocation` (`invocationNum == 0`) + transcript read | `UserPromptSubmit` |
| `tool.proposed` | `PreToolUse` | `PreToolUse` |
| `tool.completed` | `PreInvocation` transcript tail (`PostToolUse` has no payload) | `PostToolUse` |
| `tool.failed` | `PreInvocation` transcript tail | `PostToolUseFailure` |
| `model.about_to_run` | `PreInvocation` | `PostToolBatch` (closest equivalent) |
| `subagent.started` | n/a (E8) | `SubagentStart` |

### 5.3 Injection semantics

| | Antigravity | Claude Code |
|---|---|---|
| Soft context | `injectSteps` → `ephemeralMessage` (persistence unknown, E1) | `additionalContext` (persistence to be confirmed, C2) |
| Block with explanation | `PreToolUse` `deny` + `reason` | `PreToolUse` `permissionDecision: "deny"` + `permissionDecisionReason` |
| Ask the human | `ask` / `force_ask` | `ask` |
| Async push | None | `asyncRewake` (exit 2 → system reminder); plugin monitors |

The delivery ledger (spec §7.1) dedupes in both, whatever the persistence semantics turn out to be.

### 5.4 One generated rule file for both harnesses (to test)

In esp32-app-foundation, `.claude` is a symlink to `.agents`, so `.claude/rules/` **is** `.agents/rules/`. That makes a zero-code native delivery floor possible: generate one compact rule per subsystem (invariants, ruled-out approaches, failure signatures; ≤ ~1.5k tokens) into `.agents/rules/`, with frontmatter for both harnesses:

- Claude Code reads only `paths:` and ignores other keys.
- Antigravity would read its own glob activation keys.

If each harness ignores the other's keys (experiment C6, alongside the spec's E4), then touching OTA files loads the OTA rule in both harnesses with no hooks running at all.

Two limits:
- **Antigravity** scans only immediate children of `.agents/rules/`, so the generated files must sit at the top level.
- **Budget.** Unscoped rules load every session in both harnesses. Only path-scoped ones may be generated, to protect the rules budget.

This gives a **degraded mode that works natively in both**: map include + path-scoped rules + MCP pull tools, with no hooks and no tick.

## 6. Recommended dual-harness structure

> Superseded in detail by SPEC §18 (Go package layout, harness interface and capability flags). The structure below remains the conceptual map.

```
repo-memory/                          # one source repository
├── core/                             # harness-neutral: pipeline, claims, views, index,
│                                     # job table, tick, MCP server, normalised events
├── adapters/
│   ├── antigravity/                  # transcript parser, hook I/O, agy executor,
│   │                                 # agentapi reports, sidecar definition
│   └── claude_code/                  # transcript parser (versioned), hook I/O,
│                                     # claude -p executor, desktop-task reports
├── packaging/
│   ├── antigravity-plugin/           # plugin.json, hooks.json, mcp_config.json,
│   │                                 # sidecars/tick, rules/, skills/
│   └── claude-code-plugin/           # .claude-plugin/plugin.json, hooks/hooks.json,
│                                     # .mcp.json, skills/, marketplace entry
└── tests/fixtures/{antigravity,claude_code}/<version>/   # transcript corpora
```

**Adapter interface.** Each harness implements the same small set of methods:

| Method | Purpose |
|---|---|
| `discover_transcripts(since)` | Sweep support |
| `parse_transcript(path)` → steps | Parser |
| `normalise_hook(event_json)` → event | Hook input |
| `render_injection(items)` → output JSON | Hook output |
| `run_housekeeping(system, payload, schema, model)` → result + usage | Executor |
| `start_report(title, prompt)` → handle | Report surface |
| `schedule_install()` | Tick scheduling |

**Per-machine configuration** (`<data-dir>/config.yaml`):
- `housekeeping.executor: agy | claude` (default `agy` where Antigravity is installed, per your quota preference);
- `reports.surface: antigravity | claude-desktop`;
- `tick.trigger: sidecar | async-hooks | os-scheduler` (more than one is allowed; `tick.lock` dedupes).

**Shared data directory.** Both adapters write the same `<data-dir>/<repo-id>/`. Claude Code's `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`) holds only plugin-installed dependencies, so the two harnesses never split state.

## 7. Feasibility and risks

| Risk | Severity | Mitigation |
|---|---|---|
| Claude Code transcript format changes between releases (the product ships frequently; 2.1.284 today, and the hook list now has 32 events) | High | Versioned tolerant parser, fixture corpus, canary on update, hook side-log (§4.5) |
| No native command scheduler in Claude Code | Medium | Antigravity tick when co-installed; async-hook ticks; optional OS scheduler (§4.2) |
| Two authentication setups and two quotas | Medium | One executor per machine, chosen in config. The standalone Claude CLI must be signed in separately from the desktop app (§4.4). |
| Different injection semantics (`ephemeralMessage` vs `additionalContext`) | Medium | Normalised injection with ledger dedupe; E1 and C2 settle the semantics |
| Auto memory duplicating or contradicting repo memory | Medium | Import as evidence; steer via `CLAUDE.md` (§4.6) |
| Auto memory or subagent memory restating pushed claims, then being imported as support for them (circular evidence) | Medium | Exposure-aware import through `originSessionId` (§4.7, note 2); C8 measures how often it happens |
| Test matrix: 2 harnesses × 3 OSes × harness versions | Medium | Shared core tested once; adapters tested against fixtures; hook contract tests per harness |
| Hook API drift in either harness | Medium | Thin adapters, contract tests, and a `repo-memory doctor` that checks hook registration and delivery end to end |
| Async hook lifetime unknown | Low | Jobs are durable; the next trigger completes the work (C3) |

Nothing found makes a dual-harness architecture infeasible. The worst case on Claude Code is capture plus native delivery (map, path-scoped rules, MCP tools), with processing done by the Antigravity tick or an OS scheduler entry. That is already a useful system.
